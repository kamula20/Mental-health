# Between machine learning implementation

This implementation follows the 39-page `COMPLETE PROJECT.pdf`: predict three classes from self-reported social-media habits, compare Logistic Regression, Decision Tree and Random Forest, and integrate the selected model into Flask. **All training and evaluation data are synthetic.** This completes a working software demonstration; it does not validate a clinical prediction tool or fulfil the proposal's primary-data collection objective.

## Run and reproduce

From the project root, with Python 3.10–3.12:

```powershell
python -m pip install -r requirements.txt
python app.py
```

The trained model is included in `ml/artifacts/`. Starting Flask loads it once; requests do not train a model. No API key, external ML service, internet connection or separate model server is needed after installing dependencies.

To reproduce the dataset and fitted model:

```powershell
python -m ml.generate_data --samples 6000 --seed 2026
python -m ml.train --seed 2026
python tools/plot_ml_evaluation.py
python -m pytest -q tests
```

Plotting uses the optional development dependency matplotlib. Use the same Python environment for all commands. If using a virtual environment, replace `python` with `.\.venv\Scripts\python.exe`. Restart Flask after retraining. Reproduction preserves data, splits and model settings; timestamps and binary artifact hashes may change between builds or library environments.

`ml/analysis.ipynb` provides an equivalent walkthrough. Jupyter itself is optional; the command-line pipeline is sufficient. The notebook contains executable cells rather than fabricated saved outputs.

## Try the integration

1. Start the app and open `http://127.0.0.1:5000`.
2. Choose **Start my assessment**, enter `BETWEEN-DEMO`, complete the example answers and submit. Each access-code entry creates a new fictional participant, avoiding the named account's one-submission limit.
3. The young person's summary shows the saved Low/Moderate/High result, a plain-language explanation of contributing answers, their review status separately, and support information. Numerical probabilities, model versions and training details remain in the staff view. A Low model class does not establish that someone is safe or well; no class represents clinical urgency.
4. Sign in as `counsellor@between.demo` with `BetweenDemo!26`. Open the newly assigned case. The saved prediction appears as **Research model estimate** in the case and printable report, with expandable model information and class probabilities.
5. Sign in as `researcher@between.demo`. **Model status** shows model comparisons, test metrics, per-class sensitivity and specificity, a confusion matrix, feature importance and data-cleaning counts. **Data quality** explains the dataset.
6. Preloaded `P-...` records retain their original fictional outputs and are labelled **Preloaded example**. They were not generated by this trained model. Existing submissions are not silently rescored.

## Dataset and generator assumptions

`python -m ml.generate_data` writes **6,066 rows**:

| Rows | Purpose |
| ---: | --- |
| 6,000 | Unique fictional people aged 13–24 |
| 60 | Exact duplicate participants, to demonstrate deduplication |
| 6 | Invalid ages, category codes or simulated outcome totals |

About 2.5% of each input is independently masked to exercise missing-data processing. All IDs begin `SYN-`; no real names, usernames, contacts, messages, school identities or clinical records are generated or read. Gender and education are synthetic background fields retained for inspection, with **no effect in the generator's outcome formula and no use as prediction inputs**. No demographic fairness claim follows from this choice.

Daily usage, passive engagement, active engagement, night usage and platform count are correlated through an invented digital-intensity variable. Cyberbullying exposure is sampled separately. Simulated depression/anxiety totals are stochastic binomial draws with latent context and independent noise, bounded to 0–27 and 0–21 respectively. They are **not administered PHQ-9/GAD-7 questionnaires, diagnoses, measured symptom scores, or a validated model of those instruments**. WEMWBS is not simulated or scored.

All coefficients, prevalences, missingness rates and latent distributions in `ml/generate_data.py` are engineering assumptions. They were not estimated from Kenyan youth or published effect sizes. Synthetic data can only show that the software learns relationships that the generator introduced. It cannot establish those relationships in real populations, test the proposal's causal or real-world predictive hypotheses, or demonstrate early warning before illness.

## Provisional target definition

The proposal names Low/Moderate/High but does not prescribe how three classes are derived from its several instruments. Pending a supervisor-approved definition, this implementation uses the **maximum of two simulated totals**:

| Maximum simulated total | Training class |
| --- | --- |
| 0–9 | Low |
| 10–14 | Moderate |
| 15+ | High |

The boundaries use familiar symptom-score bands as an illustrative starting point. **Combining the two instruments and collapsing them into these classes is this project's provisional convention, not a validated clinical classification.** It merges minimal/mild and several higher severity bands. It must not be described as an official PHQ-9, GAD-7 or WEMWBS risk scale.

Reference score bands: [University of Washington depression screening guidance](https://www.hiv.uw.edu/go/basic-primary-care/screening-mental-disorders/core-concept/6) and [GAD-7 guidance](https://www.hiv.uw.edu/page/mental-health-screening/gad-7). These references do not validate the synthetic generator or the combined project target.

## Feature contract and questionnaire differences

`ml/schema.py` defines `between-features-1`, shared between inference and training:

| Input | Accepted values |
| --- | --- |
| age | Integer, 13–24 |
| daily_time | under1, 1to3, 3to5, 5plus |
| passive, active, night | never, rarely, sometimes, often, always |
| cyberbullying | never, once, sometimes, often |
| regular_count | 1, 2, 3, 4plus (strings) |

The model uses six behaviour features and age. Gender, education, platform identities, free text, contact preferences, consent, IDs, outcome totals, class labels and clinician decisions are excluded. Platform count is already captured by `regular_count`; the app distinguishes platforms used regularly from those selected generally.

Appendix A is present on PDF pages 36–37. The app currently merges the proposal's 1–2 and 2–3 hour choices into 1–3 hours, distinguishes college/university, offers additional gender choices and includes WhatsApp/X. Training deliberately matches the existing `behaviour-demo-1` app codes instead of silently changing previously saved answers. A future questionnaire change requires a new version and an explicit mapping/retraining decision.

## Cleaning, preprocessing and evaluation

1. Validate columns, synthetic provenance, ID format, age, category codes and bounded integer outcome totals. Reject invalid rows. Reject conflicting records sharing an ID; remove exact duplicate IDs.
2. Recompute labels from the simulated outcomes; never trust a supplied `risk_class` column as ground truth.
3. Split unique fictional participants **70% train / 15% validation / 15% test**, stratified by class and seeded. In this dataset that is 4,200 / 900 / 900. Participant IDs do not cross splits. Independently generated participants can share a behaviour profile; they are not longitudinal observations of the same person.
4. Fit median age imputation, age standardisation, categorical mode imputation and one-hot encoding **inside each training fold** using a scikit-learn `Pipeline` and `ColumnTransformer`. No statistics are learned from validation or test data during tuning. Encoding uses fixed schema categories.
5. Tune each classifier in three stratified training folds using macro-F1. Compare regularisation/tree settings and ordinary versus balanced class weights. Balanced class weights are learned from each training fold, without oversampling the validation/test sets.
6. Compare the three tuned candidates on validation macro-F1. Select the winner, calculate global permutation importance using validation only, refit that configuration on train+validation, and evaluate the final fitted model on the test partition. Only the selected model and a fixed class-prior baseline are tested.
7. Store accuracy, macro precision/recall/F1, macro one-vs-rest ROC AUC, per-class precision/sensitivity/F1 and one-vs-rest specificity. Confusion-matrix order is explicitly **Low, Moderate, High**; rows are actual and columns predicted. The baseline predicts the most common training class.

An initial development run without class weighting had poor Moderate-class recall on validation data. Class weighting was added to the candidate search. Development also inspected a preliminary test report, so this test partition should be described as a **development holdout**, not an independent external validation cohort. No test rows enter model fitting or automated model selection. A final untouched real-world cohort is still required for any defensible clinical or generalisation claim.

The stored model selected **Logistic Regression**, with 61.4% synthetic-test accuracy, 0.587 macro-F1 and 0.774 macro AUC, versus 43.4% baseline accuracy. Moderate-class sensitivity is approximately 43.7%, demonstrating substantial uncertainty. These values are measured simulation results, not acceptance targets. The proposal's real-world AUC ≥0.75 hypothesis remains untested.

Class weights change model probability estimates. The displayed probabilities are **uncalibrated simulation class outputs**, not probabilities that a real person has depression/anxiety. No per-person causal explanation is generated. Permutation importance measures associations learned from the simulator and can be affected by correlated inputs.

### Individual result explanations

For the selected multiclass Logistic Regression model, individual explanations use the actual fitted coefficients and encoded answers. They contrast the chosen class with the runner-up, relative to a reference made from training median age and modal behaviour answers. Encoded-column contributions are summed back to the original questionnaire inputs. The baseline class margin plus all grouped contributions exactly reconstructs the selected-versus-runner-up log-odds; tests check that equality.

The participant sees up to three behavioural answers with positive contributions toward the chosen class. If only opposing contributions are available, the page explains that those answers moved toward the alternative class while the overall result remained in the chosen class. If behaviour answers match the reference, it explains that no single reported habit stood out. The page does not display numerical contributions, claim causation, use global importance as a personal explanation, or invent clinical reasons. Age is included in the complete staff-accessible explanation but excluded from the short participant list. If no compatible explanation is available, the page says so. Clinician records and reports show the same plain-language explanation alongside their technical model information.

New predictions save their explanation and artifact fingerprint with the original result. Older snapshots can receive a read-time explanation only when the current model version and all saved class probabilities reproduce; a fingerprint mismatch prevents this when present. This does not update the saved classification or prediction snapshot. Unsupported model types return no explanation until a suitable method is implemented. These explanations account for the model's computation; they do not validate its health interpretation.

For the preprocessing rationale, see [scikit-learn's data leakage guidance](https://scikit-learn.org/1.5/common_pitfalls.html).

## Flask persistence and failure behaviour

`ml/service.py` loads the trusted local artifact at app creation, validates checksums, schema, model/report version, scikit-learn compatibility and class labels, and exposes `predict()` and `status()`. `requirements-ml.txt` pins the fitted model's main numerical dependencies. Joblib uses Python pickle: **only load locally generated, developer-controlled artifacts**. Checksums detect accidental corruption; they do not authenticate hostile replacements. There is no model-upload or remote artifact-loading API. See [scikit-learn persistence guidance](https://scikit-learn.org/1.5/model_persistence.html).

New submissions validate the full assessment first, then infer using only the feature allowlist. Complete inputs are required at serving time: training-time imputation is not an excuse to turn incomplete submissions into a Low result. A dependency, missing-file, integrity, version or prediction error leaves a clear unavailable result; submitting answers still succeeds. No fallback class or default probability is invented.

The `model_predictions` table is created additively for existing databases. Its participant-keyed JSON snapshot is written in the same transaction as the assessment and includes class, class probabilities, source, version and limitation text. Submission retries return that snapshot. Reads, clinician reviews and model replacement do not rescore it. Original seeded outputs remain recognisable legacy examples.

`GET /api/model` returns aggregate model metadata to clinicians, Insights and administrators. `GET /api/research` includes the same metadata for Insights. Neither includes participant rows. Existing role, assignment, CSRF, draft, consent and review controls remain in force. The model does not alter review status, trigger notifications, invent psychometric scores, ingest app submissions for training or unlock live enrolment.

To use another trusted artifact directory in a test/deployment entry point, pass `ML_ARTIFACT_DIR` through `create_app({...})`. This is a server configuration, not a browser or public environment switch. Restart the process to load a replacement.

## Before replacing synthetic data

A real study needs an approved target/protocol, appropriately administered and permitted outcome instruments, actual consent/assent, independently collected labelled data, population-specific error and fairness analysis, calibration and a separate external evaluation. Longitudinal claims need longitudinal outcomes. Keep held-out participants and institutions separate as the study design requires, and have the appropriate professionals review how outputs are used.

Do not present these synthetic rows as questionnaire respondents or the measured simulation metrics as evidence about Kenyan youth. No instrument wording or licences have been added, no real study has been conducted, and app support remains an unmonitored demonstration.
